{# **The settings, one topic at a time**, and the pattern is `km-package-builder`'s `.curate` strip by way of `km-admin`'s copy of it: flat radio siblings and `:checked ~`, no JavaScript. Two things about it are load-bearing rather than stylistic. **The radios are flat siblings of the panes.** A strip that wrapped each pane would need `:has()` to reach sideways out of itself, and `.pane { display: none }` is unconditional -- so a browser that could not evaluate that would show *no* pane and this tab's whole settings half would be gone. `:checked ~` has worked for a decade, and a stylesheet that fails to load leaves every section on the page. **They sit outside every form.** A radio inside a form would post a `machine-tab` key nobody reads. A test asserts this by position. **A pane is a topic, named for what it holds**, everyday first and the developer's last. Both hosts draw the same five, because `Two admin surfaces, one vocabulary` requires a page on both to be named the same in the same place. A card one host lacks leaves its pane, never the strip. General opens, because it is the one pane that is never empty. **A save comes back to the pane it was made on.** The pane rides in the redirect's query string, is checked against a fixed list of names by `handlers::back_pane`, and an unknown one opens General -- so nothing a caller sends reaches the `checked` attribute or the redirect. #}
